WKND Site Analysis — Edge Delivery Services Readiness Report

An analysis of https://wknd.site/us/en.html and the wider WKND site, assessed against Adobe Edge Delivery Services (EDS) principles. This report maps the existing experience to EDS sections and blocks, evaluates the content and authoring model, reviews performance and accessibility, and estimates the scope of a migration.

Prepared: August 2026  ·  Source site: WKND Adventures & Travel (Adobe demo)  ·  Locale in scope: /us/en

1. Executive Summary

WKND is a content-rich travel and adventure site built on classic AEM Sites with Core Components. Its content is highly regular — a small set of page types repeated across many pages — which makes it an excellent candidate for Edge Delivery Services. The visual language is card-driven, image-led, and consistent, so a compact block palette can cover the whole site.

The homepage decomposes cleanly into six EDS sections built from four reusable blocks (hero, cards, teaser/columns, and carousel). Across the site, roughly 7 page templates and an estimated 10–12 blocks would cover all content. The two areas needing the most design attention are the adventure-detail metadata panel and the tabbed detail sections; everything else maps to standard boilerplate blocks.

3. Homepage — EDS Section & Block Decomposition

Following EDS principles, the homepage is a sequence of sections (separated by three dashes in a document, or top-level divs in markup). Each section is either default content (headings, text, buttons, images) or a block. Below is the recommended decomposition.

5. Content Model & Authoring Approach

EDS blocks are authored as simple tables; the content model is the contract between author and developer. The key models below keep authoring intuitive and forgiving of missing fields.

cards (article / adventure / profile)

One row per card. Column 1 = image; column 2 = text (title as a link, then summary). A section-level variant class (cards (adventure)) switches styling. Authors add or remove rows freely; the grid reflows responsively.

columns teaser

A single row with two cells: image in one, heading + body + a linked CTA in the other. Swapping cell order gives image-left vs image-right without new code.

fact-panel (adventure detail)

A two-column key/value table: label in the left cell (Price, Trip Length, Group Size, Difficulty, Activity), value in the right. The block renders it as a compact definition list. Authors only fill the values they have.

tabs (adventure detail)

Each row is a tab: cell 1 = tab label, cell 2 = tab body (rich content). Authors reorder or drop tabs by editing rows.

Authoring recommendations

  • Convert the static FAQ "bold question + paragraph" pattern into an accordion block for better scannability, while keeping the underlying content as plain heading/paragraph pairs so it degrades gracefully.
  • Use section metadata for background/style variations (e.g. the "highlight" style already used in the boilerplate) rather than bespoke blocks.
  • Lean on autoblocking for hero and article headers so authors write a normal H1 + image and the block is built automatically.
  • Model the language/region selector via metadata + a fragment, not a hand-built block, so it stays consistent across locales.

6. Performance Review (Keeping it 100)

EDS targets a perfect Lighthouse score through eager/lazy/delayed phasing and image optimisation. The current WKND site relies on Core Components and client libraries; the migration is an opportunity to hit those targets by default.

AreaCurrent riskEDS recommendation
LCPHero image is large and homepage is image-heavyMake the hero image the eager-loaded LCP candidate; size it responsively; avoid lazy-loading it
CarouselCarousels commonly ship heavy JS and block renderingLoad carousel JS lazily; render first slide as static markup; use CSS scroll-snap where possible
ImagesMany full-width photosRely on EDS auto-optimised picture element with width/format params; set explicit width/height to avoid CLS
FontsCustom brand fontsPreload and use font-display: swap; define in fonts.css; keep fallback metrics close
Third-partySocial share widgetsDefer to the delayed phase via delayed.js
CSS/JS weightGlobal client librariesMinimal styles.css for LCP; per-block CSS/JS via automatic code splitting

Target: PageSpeed Insights 100 on the feature-preview URL before merging, per the project's publishing process.

Reuse vs net-new

  • Reuse from boilerplate / Block Collection: header, footer, hero, cards, columns, quote, embed.
  • Net-new (or Collection + styling): carousel, tabs, fact-panel, author-bio, listing filter.
  • Autoblocking candidates: hero and article-header — reduces authoring burden and net-new code.

9. Recommended Next Steps

  1. Confirm the block palette (Section 4) and lock content models with the authoring team.
  2. Build/style reuse blocks first (hero, cards, columns, footer, header), then the net-new detail blocks.
  3. Generate import infrastructure per template and run a template-driven bulk import.
  4. Validate each imported template against the source (content completeness + visual critique).
  5. Run PageSpeed Insights against feature-preview URLs; iterate to a score of 100.
  6. Complete an accessibility pass (headings, alt text, carousel/tabs keyboard support) before go-live.

This report scopes the migration; it does not perform it. Actual block development and content import are separate, subsequent phases.
